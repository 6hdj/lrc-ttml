## 3. 已完成的裁剪与实测结果（阶段 B）

### 3.1 决策依据：一次**带阴性对照**的 CUDA 依赖实测

`tools/size_report.py` 定位的真相：**CUDA 占 64.6%**、PyTorch 14.5%。
所以先解决最大的那一块 —— CUDA 到底需要哪些文件。

实验脚本 `.tmp/exp_cuda_quick.py`，真 RTX 4060、真音频（30 秒片段）：

| 保留哪些 CUDA 库 | GPU int8_float16 | GPU float16 | 同环境 CPU（对照） |
| --- | --- | --- | --- |
| 全套（cuDNN 1095 + nvrtc 178 + cuBLAS 736 MiB） | 2.60s | 1.50s | 9.39s |
| 去掉 cuDNN（−1095 MiB） | 1.65s | 1.48s | — |
| **只留 cuBLAS**（−1273 MiB） | **1.59s** | **1.43s** | 9.46s |

⇒ **cuDNN 与 nvrtc 都不是必需依赖**，去掉后还更快。
GPU 确实在工作：CPU 9.4s vs GPU 1.4–1.6s，**差 6 倍以上**。

> ⚠️⚠️ **这个结论是第四次实验才拿到的，前三次全错，而且错得很像结论**：
> ① 模型缓存没命中 → `WhisperModel` 联网超时，6 轮全 FAIL（其实没走到转写）；
> ② 子进程里 `sys.executable` 是**系统 python** → `import asr` 失败，
>    却被误报成 "cublas 缺件"；
> ③ **最坑的一版**：7 轮全部"成功"，**包括故意留空的阴性对照** ——
>    因为 `compute_type="float16"` 那条路根本没走 cuDNN，
>    CTranslate2 静默换了实现。
>
> **方法学教训（以后的"裁剪类"实验都要遵守）**：
> 任何"删掉 X 还能跑"的结论都不成立，除非同时有一个
> **"删掉 X 必须挂"的对照**。本次的对照是"拿掉 cublas →
> `device="cuda"` 直接失败"，它证明实验**能测出坏**。

### 3.4 PyTorch 移出主包（用户确认后实施）

需求原文 §七-B 允许"把可独立部署的运行组件做成按需下载"。用户确认后实施：

* **先查清依赖边界**（需求第 5/6 条）：全仓 `grep`，生产代码里 `import torch`
  的只有 `speaker_campplus.py`（CAM++ 声纹）与 `separate.py`（Demucs，本就不在包里），
  加上 `asr._detect_device`/`doctor`/`envcheck` 的**探测**（可缺省）。
  ⇒ **基础歌词制作、单声部处理、TTML 编辑与导出都不需要 torch。**
* **版本钉死**（需求第 5 条）：`torch 2.14.1`、`cp314-cp314-win_amd64`、
  124110781 字节、SHA256 `d02a4c48…ca956`，见
  `desktop/resources/runtime_manifest.json`。依据：与仓库 `.venvpack` 实测在用的
  版本一致；且实测它的 `Requires-Dist` 里所有 `nvidia-*` 都带
  `platform_system == "Linux"` —— **Windows 上不拉任何 CUDA 包**。
* **实测 `import torch` 真正需要哪些依赖**（`.tmp/torch_import_deps.py`，逐个屏蔽法）：
  元数据列了 8 个 `Requires-Dist`，但**真正必需的只有 `filelock` + `typing_extensions`**
  （sympy / networkx / jinja2 / fsspec / mpmath / markupsafe 都不需要）。
  这两个主包已经带了 ⇒ 运行时组件**只下一个 wheel**。
* **隔离验证**（`.tmp/verify_runtime_campplus.py`）：把进程 `sys.path` 收成
  **只有运行时目录那一份 torch**，真下 CAM++ 权重、真解音频、真跑 `embed()`：
  ```
  torch 2.14.1+cpu
    来自: .tmp\rt-campplus\runtime\torch\torch\__init__.py   ← 确认不是开发环境那套
  speaker_campplus.available() = True
  ✓ embed() 返回 (192,) 维向量，范数 1.0000
  ✓ 可重复性：两次结果一致 = True
  ```
  ⇒ **PyTorch 可以安全移出主包**，CAM++ 能真跑出 192 维声纹。

配套改动（缺一个就会静默降级）：
1. `desktop/services/runtime_service.py` —— 下载/校验/解包/真加载验证的状态机，
   装在 `<数据目录>/runtime/<id>`（**用户可写**，不进程序目录、不进 `_MEIPASS`）；
   `.part` 失败不删（续传）、SHA256 校验、解包防目录穿越、磁盘空间预检。
2. `paths.apply_runtime_path()` + `launcher._rehome()` —— 在**任何 `import torch` 之前**
   把运行时目录插进 `sys.path`；**命令行与窗口两条路都覆盖**（只放 `app.py` 会漏掉 CLI）。
3. `speaker_campplus.available()` 把"torch 能不能 import"算进判据，
   并新增 `missing_reason()` —— **运行时缺失与权重缺失分别给文案**（需求第 9 条）。

### 8.1 先补上测试盲区：截图里中文全是豆腐块

`desktop/uicheck.py --shot` 出来的截图里**所有中文都是 □□□**。查下来是

## 7. 本轮（第 3 轮）：正式分发 —— 无黑窗 + 外壳集成

### 7.1 双击不再弹黑色控制台窗口（**已实测**）

用户明确要求"正常使用时不弹出黑色控制台窗口"。原来 spec 里是 `console=True`，
所以双击必弹黑窗。

⚠️ **`console=False` 是错的**（第一版就这么改，被实测否掉）：
GUI 子系统进程**不继承父进程的标准句柄**，于是
```
Lyric2TTML.exe --doctor --json > out.txt     # 写出来是 0 字节
powershell ... 2>&1 | ...                    # 什么都抓不到
```
会把**脚本、CI、以及 `tools/accept_frozen.py`**（它靠捕获输出来判定）全部搞坏。

✅ **正确做法**：`console=True` + `hide_console='hide-early'`（PyInstaller ≥6.0，
本机 6.22.3）。exe 仍是**控制台子系统**（句柄照常继承、重定向照常工作），
但**窗口在启动早期被隐藏** —— 双击/快捷方式启动时看不到黑窗。

实测（`dist/_build2`）：

| 检查 | 结果 |
| --- | --- |
| PE Subsystem | **3**（控制台子系统，句柄可继承） |
| `--version > v.txt` | **470 字节**（`console=False` 时是 **0**） |
| `--doctor --json > d.txt` | **4782 字节**（同上，之前 0） |
| `--help` | 正常 |
| 双击/快捷方式 | 无黑窗（`hide-early`） |

⚠️ 想临时看到控制台排查启动问题：`L2T_WITH_CONSOLE=1` 重新打包。

### 7.2 新增 `win_integration.py`：开始菜单 / 桌面 / 卸载注册表项

现状（改造前）：安装器**只**建了一个指向 **`启动.bat`** 的桌面快捷方式 ——
那既会带出黑窗，用户看到的还是"批处理"；**没有开始菜单项**；
**没有写"已安装的应用"注册表项**，所以 Windows 设置里根本看不到它。

新增的模块（安装与卸载**共用同一份逻辑**，避免两边漂移）：

* **开始菜单**：`<APPDATA>\Microsoft\Windows\Start Menu\Programs\Lyric2TTML.lnk`
  → 指向 **`Lyric2TTML.exe` 本体**（不是 .bat）。
* **桌面**：同一份逻辑，**默认不建**（安装界面里有勾选框，符合"避免未经同意创建"）。
* **卸载注册表项**：HKCU 的
  `Software\Microsoft\Windows\CurrentVersion\Uninstall\Lyric2TTML`，
  写 `DisplayName / DisplayVersion / Publisher / InstallLocation /
  UninstallString / QuietUninstallString / DisplayIcon / EstimatedSize /
  NoModify / NoRepair`。
  * 用 **HKCU 而不是 HKLM**：普通用户就能写，**不需要管理员**（与项目原则一致）。
  * `reg add /f` **幂等**：重复安装不会叠加条目。
* `integrate_remove()` 与安装**对称**：删快捷方式 + 删注册表项，全部幂等。

实测（沙箱目录，沙箱路径用 `--programs/--desk` 注入）：

```
[完成] 开始菜单快捷方式：…\.tmp\wi-test\programs\Lyric2TTML.lnk
[完成] 桌面快捷方式：…\.tmp\wi-test\desk\Lyric2TTML.lnk
[提示] 卸载注册表项没写成功（不影响使用，但设置里看不到它）
```
前两项**确认生成成功**（`Get-ChildItem` 列到了 .lnk）。

⚠️ **注册表那一项没能在本会话验证**：`reg add HKCU\...` 返回
`ERROR: Access is denied.` —— 本会话的**文件/注册表沙箱**把 HKCU 写入也拦了
（不是代码问题：HKCU 正常用户可写，`reg add /f` 命令本身是标准的）。
⇒ 记为**未验证**，需要在正常权限下复测。

### 7.3 新增 `tools/clean_build.py`：救活被卡住的构建流水线

⚠️ 真踩到，而且**卡住了整条构建**：PyInstaller 开始前会
`shutil.rmtree(distpath)`，而上一次跑测试时主程序把自己的模型缓存写到了
`<dist>/Lyric2TTML/.hf_cache/`；中断的下载留下 `tmp*` 目录 + **只读属性**，
于是 `shutil.rmtree` 报 `WinError 5` 直接失败，`ignore_errors=True` 也救不了。

解决：① 递归清只读/隐藏/系统属性；② 用 `robocopy <空目录> <目标> /MIR`
把目标**镜像成空**（比 rmtree 强得多）；③ 再删空壳。
`--probe` 只报告不删。

## 4. 本轮发现的真 bug（已修）：打包版在 CPU 上静默慢跑

修 CUDA 裁剪时发现：**打包版转换要 556 秒，源码模式只要 31 秒**（同一首歌）。

**根因**：`asr._register_cuda_dlls()` 用
`for base in sys.path: glob(base + "/nvidia/*/bin")` 找 CUDA DLL，
**赌 `_internal` 在 `sys.path` 上**。赌输时 `WhisperModel(device="cuda")` 抛
`Library cublas64_12.dll is not found or cannot be loaded`，
而 `ensure_loaded()` 把它当"显卡不可用"→ **退到 CPU**
→ 用户看到的是"慢得离谱"，而不是报错。
（这正是之前观测到的"冻结版 815 秒 vs 源码 25 秒"的真身。）

**修法**：不再赌 `sys.path`，显式扫 `sys._MEIPASS` / exe 同级 /
`<app>/_internal/nvidia/*/bin` / `<app>/cuda`。
同时把 `gpu_probe.cuda_dirs()` 改成同一口径（它原来**完全不看**
`_internal/nvidia`，两个函数不一致 → "体检说没问题、一跑就报错"），
并把 `paths._source_dir()` 公开为 `source_dir()`。

| | 修复前 | 修复后 |
| --- | --- | --- |
| **打包版转换（同一首歌）** | **555.8 s** | **24.0 s** |
| 源码模式（对照） | 31.2 s | 31.2 s |

## 6. 未验证事项 / 已知障碍（如实记录）

### 6.1 ✅ 已解决（2026-10-13，方案②）：CAM++ 改用 ONNX 后端

**原来那条"冻结版里 `import torch` 让进程 `0xC0000005` 崩掉"的障碍，已经绕过去了** ——
不是修好了 torch，而是**让分声部不再需要 torch**。

| 验证 | 结果 |
| --- | --- |
| `tools/eval_diarization.py`（原样、同一协议） | **85.0%**（4 首 / 160 行） |
| 逐首一致率 | 90.6 / 74.5 / 97.0 / 84.1 —— **与历史基线逐首完全一致** |
| 真实音频 归一化后 max\|Δ\|（ONNX vs torch） | **5.5e-04**（6 片段，51~1501 帧） |
| 真实音频 最坏余弦 | **0.999995** |
| 合成音频 max\|Δ\| | 2.3e-05（17 个长度，含生产常用的 **801 帧**） |
| 速度（CPU） | ONNX 39.9 ms/行 vs torch 38.2 ms/行（持平） |
| **冻结版端到端分声部（无 torch）** | ✅ `v1 20 行 / v2 12 行`，与该歌评估值一致 |

⇒ 用户**不必再下载 118 MB 的 PyTorch 运行时组件**，分声部在打包版也能用。
torch 后端仍保留可回退（Demucs 人声分离若要做仍需要 torch）。

**过程中发现并修掉的两个真 bug**：

1. **`avg_pool1d(ceil_mode=True)` 在 ONNX 里语义不同** ⇒ 非 100 整数倍长度全错。
   实测：200/300/400/800/900（100 的倍数）逐元素相同；199/201/301/799/**801**/901
   差 1.3e-3 ~ 2.1e+0。**801 帧 ≈ 8 秒 @16k，正是生产最常用的长度。**
   换成掩码分段均值后 ≤7.5e-8。
2. **`diarize._HAS_MODEL` 是 import 时定死的常量** ⇒ 打包版里 ONNX 图明明在包里，
   分声部却**静默退回按歌词标记**（实测产物 v1 32 行 / v2 0 行）。改成动态判断。

⚠️ 顺带记一个测试环境的坑：**冻结版会忽略 `L2T_HF_CACHE`**，
把 3 GB 模型下到 `<exe>/.hf_cache` —— 于是"转换要 565 秒"看着像
**GPU 静默慢跑**，其实是在下模型（白查一轮）。下次测冻结版请显式传
`HUGGINGFACE_HUB_CACHE`。
