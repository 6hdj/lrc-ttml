## 0. 速读结论

1. **本项目已经有竞品最缺的那一半**：离线全自动打轴流水线（ASR + 动态规划强制对齐 + 二次精修 + 声纹分声部 + 人声分离），时间戳全部来自真实音频。竞品被指出"缺 ASR 自动打轴、核心依赖人工打点"，这正是我们的主场。
2. **本项目缺的正好是竞品最强的那一半**：逐字可编辑的编辑态 + 实时逐字高亮预览。当前 Web 端生成完只能用一段静态文本 `<pre>` 预览 TTML，改不了任何一个字的时间。
3. ~~最高优先级不是"做编辑界面"，而是先补三块地基~~ → **本条第 ①② 块已落地**：TTML 反向解析（`ttml_model.py` / `ttml_reader.py`）与时间轴规范化/自动修复（`ttml_normalize.py`）已由并行会话实现；剩下的地基是 ③ **编辑态持久化 + 历史版本**（现在转换结果只活在进程内存里，而竞品已有 IndexedDB 多版本自动保存，见 §5.3）。
4. **刻意不做的**：不引入前端框架，沿用"单文件 `index.html` + 标准库 `http.server`"；不把高级参数删掉，只折叠隐藏；不做云端上传（离线是本项目的信任基础）。

## 5. 借鉴 + 重大升级（技术设计，本文档核心）

### 5.0 设计总原则

1. **复用而非新建**：编辑态数据结构直接**对齐** `AlignedLine` / `Unit`，避免第二套真相。
2. **一个真理源**：规范化算法只有一份，生成链路和编辑链路都调它（§5.2 关键结论）。
3. **闭环可解释**：任何自动改动都必须留痕（`NormalizeReport`），能在界面上说清"我改了哪几个字、为什么"。
4. **不破坏现状**：所有新增都是**新文件 + 新端点**；对现有函数的改动限定为"把内部实现抽成可复用函数"，签名与行为不变，由 `selftest.py` 锁死。

### 5.1 关键补强一：TTML 往返（round-trip）—— G1 的解

> **实现状态（2026-10-09 二次修订）**：本节已由并行会话实现，`ttml_model.py` / `ttml_reader.py` 均在仓库中；下面的字段设计保留作**对照基准**，实现与它的差异见 §3.4。

**新增文件 `ttml_model.py`**：编辑态模型（字段刻意对齐现有结构）

**★ 关键结论（避免两份逻辑漂移）**：

> `matcher.py:706/714/727` 里的三个后处理函数，本质就是"时间轴规范化"。**实现 `ttml_normalize.py` 时应当把它们抽成可复用的纯函数**（输入 `List[Unit]` + 窗口，输出修复后的时间 + 改动清单），然后：
> - **生成链路**（`matcher._finalize_line`）继续调用它 —— 行为不变，`selftest.py` 必须全绿；
> - **编辑链路**（`normalize_timeline`）调用同一份 —— 保证"AI 生成的结果"和"人工改后的修复"遵循**完全相同**的时间规则。
>
> 否则迟早出现"自动生成时允许的重叠，手动改一下就被判非法"这种自相矛盾体验（正是竞品 B2 的观感来源）。

**策略语义**：
| policy | 行为 | 用在 |
|--------|------|------|
| `auto` | 全部自动修，产出 `fixes`，前端提示"检测到 N 处时间冲突，已自动修复，可复核" | 默认；对应 B2 的对策 |
| `highlight` | 不落盘，只返回冲突位置，前端标黄 | 用户勾选"先别改我的" |
| `off` | 只校验不修复 | 导出前最终确认 |

### 5.3 关键补强三：异常处理与进度保留 —— B3 / G6 / G7 的解

**后端**
- 编辑态落盘：`outputs/<task_id>.edit.json`（`EditDoc` 的 JSON 序列化，含 `meta` + `version`）。
  - **原子写**：写 `*.tmp` → `os.replace()` 覆盖，避免半个文件。
  - 服务启动时不需要全量加载；`GET /api/edit?id=` 时若内存缺失则尝试从磁盘恢复，恢复后写一条日志。
- 统一错误响应契约（替代现在的裸 500）：

```json
{ "error": "人类可读的中文原因",
  "where": { "line_key": "L7", "word_index": 3 },
  "detail": "可选的技术细节",
  "hint": "可选：下一步建议做什么" }
```
  实现上：在 [web_server.py:169-179](\web_server.py) 的 `do_POST` 已有的 `except Exception` 里，增加对自定义异常 `TTMLEditError(error, where, detail, hint)` 的分支，HTTP 用 400/409 而不是 500。**保持现状的"不崩"特性**（[web_server.py:311-318](\web_server.py) 已经是这个哲学，只是信息没结构化）。

**前端**
- 每次编辑后把 `EditDoc` 写入 `localStorage`（key 带 `task_id`），节流 500ms；载入时若后端恢复失败则用草稿。
- 任何 API 报错：**只弹定位提示，绝不清空编辑区**；提供"重新载入后端版本"与"用本地草稿覆盖"两个显式选择。
- 版本冲突（409）：提示"内容已在别处改动"，显示差异行号，由用户选择保留哪一份。

### 5.4 工作流分层

```
【自动阶段（默认首选）】  导入音频 + 歌词 → 现有流水线 → 逐字时间轴 + 自检报告
                              │  （生成结果 = EditDoc，写入 outputs/<id>.edit.json）
                              ▼
【微调阶段（少量使用）】  进入编辑台 → 只改极少数匹配率低的字 → 自动规范化 → 复核清单 → 导出
```

- 两个阶段**共用同一份模型与同一份规范化算法**；
- 微调阶段**绝不重跑 ASR**：拖动某个字只触发"规范化 + `check_ttml`"，本地毫秒级完成；
- 给用户一个"哪几行最该看"的入口：直接复用已有的 `Unit.matched` / `prob`（[matcher.py:107-109](\matcher.py)），把 `matched=False`（插值补的）和 `prob` 低的字在编辑区标灰/标黄。README 的"逐字误差 ±50~150ms"和"0.06s 的字是插值"两条 FAQ 正是这个功能的用户故事。

### 5.5 API 设计（在现有 7 个端点上新增，风格与 `_json`/`_file` 一致）

| 方法 | 路径 | 入参 | 返回 | 说明 |
|------|------|------|------|------|
| GET | `/api/edit` | `?id=<task_id>` | `{doc, version, source}` | 由 `task.ttml` 经 `parse_ttml` 得到；内存无则从 `.edit.json` 恢复，`source` 标 `memory`/`disk`/`draft` |
| POST | `/api/edit` | `{id, version, doc}` 或 `{id, version, patches[]}` | `{doc, version, normalize, check}` | 乐观锁：`version` 不匹配返回 409；成功后跑规范化 + 校验 + 原子落盘 + 更新 `task.ttml` |
| POST | `/api/validate` | `{doc}` 或 `{ttml}` | `{normalize, check}` | 只算不写，供预览侧实时调用（前端节流 ≥300ms） |
| GET | `/api/audio` | `?id=<task_id>` | 音频字节流 | 支持 `Range`（播放器 seek 必需）；**必须校验解析后的绝对路径落在 `uploads/` 内**，防目录穿越 |
| GET | `/api/ttml` | `?id=`（**已有**） | 纯文本 TTML | 保持兼容；编辑后返回最新串 |
| GET | `/api/download` | `?id=`（**已有**） | 附件 | 保持兼容；下载前建议先跑一次 `check_ttml` |

**现有端点的位置（二次修订后的实际行号）**：[web_server.py:133-166](\web_server.py)（GET 全部分支，`/api/task`、`/api/ttml`、`/api/download`、`/api/info`）、[web_server.py:169-217](\web_server.py)（POST：`/api/upload`、`/api/convert`）。

**安全与健壮性要求**：
- `/api/audio` 的路径必须 `os.path.abspath` 后校验 `startswith(UPLOAD_DIR)`；
- 所有 POST body 走已有 `_read_json()`（[web_server.py:113-117](\web_server.py)），超大 body 需限制（现在无上限）；
- 编辑态 JSON 读取失败（文件损坏）不能 500，降级为"从 `task.ttml` 重建"。

### 5.6 预览与分栏（借 A3、A4）

- **逐字高亮**：`<audio>` + `requestAnimationFrame`，按当前 `currentTime` 在 `EditDoc.words` 里二分找命中字，加高亮 class。因为模型有精确 begin/end，这一步不需要任何 DOM 测量。
- **分栏（双人对唱）**：按 `EditLine.agent` 分组左右显示；`v1`/`v2` 是现有约定（README 第 164-171 行的标记表）。
- **和声**：`x-bg` 作为**同一行内**的嵌套内容缩进显示、可与主唱同时高亮（**不得**渲染成独立一行——见 §9.1 术语表与 [AGENTS.md:32](\AGENTS.md)）。
- **⚠️ 规范降级显示**：`x-duet-a` / `x-duet-b` / `x-narration` 是 **Apple 内部扩展，不在 AMLL TTML Database 规范里，社区解析器会忽略未知 role**（[README.md:514-516](\README.md)、[README.md:418-420](\README.md)）。预览里对这三种 role 只能作为"提示性配色"，不能据此宣称"AMLL Player 会这么显示"。
- **预览不得漂移**：预览渲染与导出的 TTML 必须来自同一 `EditDoc`。建议加一条测试：对同一 `EditDoc`，`write()` 的产物 `parse_ttml` 回来后与预览用模型逐字相等。

| TTML | Timed Text Markup Language，Apple Music 逐字歌词使用的 XML 格式 |
| AMLL TTML DB | 社区歌词库及其格式规范（`amll-dev/amll-ttml-db`） |
| `itunes:timing="Word"` | 逐字模式（另有 `Line` 逐行） |
| `ttm:agent` | 演唱者标识（`v1` / `v2` / `v3`，`person`/`group`/`other`） |
| `x-bg` | 背景人声层，**AMLL 规范内**，允许与主唱重叠。**必须作为某一行主唱的 `<span>` 子内容，绝不能单独成行**——AMLL 解析时 x-bg 不计入本行文本，单独成行 = 空行 = 播放器看不见（本仓库铁律 #8，见 [AGENTS.md:32](\AGENTS.md)；本项目已用 `preprocess.merge_background_lines()` 修复该问题） |
| `x-translation` / `x-roman` | 翻译层 / 音译层，**AMLL 规范内** |
| `x-duet-a` / `x-duet-b` / `x-narration` | Apple 内部扩展角色，**不在 AMLL 规范内**，社区解析器忽略（[README.md:514-516](\README.md)） |
| `itunes:key` | 行标识，`L1` 起连续递增，跨 div 不断号（[ttml_check.py:282-283](\ttml_check.py)） |
| `itunes:songPart` | 段落名（Verse / Chorus），`--mode apple` 时按静默间隔切 div |
| 逐字 vs 逐行 | 逐字 = 每个 `<span>` 有独立 begin/end；逐行 = 只有 `<p>` 有时间 |
| `matched` / `prob` | 该字是否真被 ASR 匹配上 / 匹配置信度；`matched=False` 的字是插值补的，是"最该人工看"的位置 |
