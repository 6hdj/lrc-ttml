# 声纹分声部评估协议（固定，改模型前先读）

> 目的：**把"这个改动到底有没有用"变成可复现的数字，而不是在某一首歌上把错行调对。**
> 工具：`tools/eval_diarization.py`　　`python tools/eval_diarization.py`

---

## 1. 真值从哪来

**AMLL TTML DB**（`amll-dev/amll-ttml-db`）里社区审核过的 `<p ttm:agent>`。
它是*人工标注*，不是模型输出，所以能当真值用。

仓库结构（每条歌词有 6 种格式）：

```
ncm-lyrics/<ncmId>.ttml        ← 人工标注在这
qq-lyrics/<qqId>.ttml
am-lyrics/<appleMusicId>.ttml
spotify-lyrics/<spotifyId>.ttml
raw-lyrics/<上传号>.ttml        （无 index.jsonl）
```

按标题找歌：各目录下的 **`index.jsonl`** 有完整元数据
（`musicName` / `artists` / 各平台 ID）。**不要**按文件名找歌名——文件名只有平台 ID。

### 网络（本机实测 2026-10-10）

| 通路 | 状态 |
| --- | --- |
| `api.github.com` | ✅ 可用（列仓库树、取 index 都能走） |
| `ghproxy.net` / `gh-proxy.com` + raw.githubusercontent | ✅ 可用（取文件正文走这个） |
| `raw.githubusercontent.com` / `cdn.jsdelivr.net` | ❌ 连接被重置 |
| `gitee` / `gitcode` 镜像 | ❌ 404 |

拉一份文件：

```
https://ghproxy.net/https://raw.githubusercontent.com/amll-dev/amll-ttml-db/main/<路径>
```

音频取自用户已上传的 `uploads/`，与 DB 标注的同一性用**歌词 2-gram 重合度**确认
（≥0.75 视为同一版本，实测这 4 首都是 0.94~0.98）。

| 歌 | 行数 | 真值 v1/v2 | 重合度 | 备注 |
| --- | --- | --- | --- | --- |
| 我不曾忘记 | 34 | 20/14 | 0.94 | |
| 在出发之前 | 33 | 18/15 | 0.98 | |
| 让风告诉你 | 46 | 32/14 | 0.95 | |
| 失眠飞行 | 51 | 39/12 | 0.98 | ⚠ **版本存疑**：DB 署名「接个吻，开一枪/沈以诚/薛黛霏」，音频是 KBShinya&hanser 版。行结构一致，但**换人翻唱时 v1/v2 的角色分配未必沿用** |

**按歌曲划分，不许同一首歌既当开发集又当验证集。**

## 3. 基线（禁止改动）

`diarize.line_embedding`（整行单次前向）+ **原始混音** + `diarize._kmeans(k=2)`。
候选方案只允许替换 embedding 提取那一步，**跨度、聚类、评估代码一律不动**。

> 为什么强制 k=2：音频内部判不出"几个人"（平均连接阈值扫描最好 59.4%、
> gap/silhouette 反向、BIC 双峰完全反了），人数只能来自元数据。

## 4. 评价指标（全都要报，不许只报总准确率）

1. **总体逐行一致率**（允许整体标签置换——v1/v2 编号本身无语义）
2. **每歌手召回** —— 某歌手召回明显低 = 他的发声状态被拆进了另一簇
3. **高音区 / 低音区** 分组准确率（按本行 F0 相对本歌中位数分）
4. **连续错行段**长度（成段 = 段落级问题，不是逐行噪声）
5. **混淆矩阵**（谁被当成了谁）
6. **x-bg 和声行**单列

## 5. 采用标准（事先约定，事后不许改）

四条**全过**才考虑替换生产模型：

1. 总体准确率提升 **≥ 2 个百分点**；
2. 提升**不能只来自 1 首歌**（要看每首歌的最小提升）；
3. **任一歌**的总体准确率下降 **≤ 3 个百分点**；
4. 必须同时改善目标错误类型（"某歌手被系统性判错"），且不显著损害普通独唱。

## 6. 基线结果（2026-10-10，改动前存档）

总体 **85.0%**（136/160，4 首）；剔除版本存疑的《失眠飞行》后 **89.9%**（98/109，3 首）。

| 歌 | 一致率 | 行数 |
| --- | --- | --- |
| 我不曾忘记 | 97.0% | 33 |
| 在出发之前 | 90.6% | 32 |
| 让风告诉你 | 84.1% | 44 |
| 失眠飞行（存疑） | 74.5% | 51 |

**每歌手召回全是单向的**（一个歌手被吸进另一个，从不双向）：

| 歌 | 召回 | 主要混淆 |
| --- | --- | --- |
| 在出发之前 | v1 100% / v2 80% | v2→v1 ×3 |
| 让风告诉你 | v1 77% / v2 100% | v1→v2 ×7 |
| 失眠飞行 | v1 67% / v2 100% | v1→v2 ×13 |
| 我不曾忘记 | v1 100% / v2 92% | v2→v1 ×1 |

### 已经排除的假设（不要再重复试）

| 假设 | 结果 | 证据 |
| --- | --- | --- |
| **高音导致声纹偏离** | ❌ **跨歌曲不成立** | 单看《在出发之前》F0↔相似度 r=−0.23、错行 F0 238 vs 194，像真的；但 4 首里《让风告诉你》低音区 75% / 高音区 95%、《失眠飞行》低音区 63% / 高音区 87.5% —— **两首是低音区更差**。单曲相关是局部现象 |
| 回归去掉 F0 影响 | ❌ | 90.6% → 90.6%（一个没改） |
| 每歌手拆低/高音区簇心 | ❌ | 53.1% / 81.2%（更差） |
| 人工参考声纹（留一法） | ❌ | 89.3% / 88.5% / 86.4%，全部 ≤ 基线 90.6% |
| 窗口平均声纹（旧实现） | ❌ | 50.0%（已改成整行） |
| Demucs 人声轨当声纹输入 | ❌ | 53.1% vs 原始混音 90.6%（已改） |
| 用音频内部判据决定"分几个人" | ❌ | 三种判据全失败，见 §3 |

### 仍然成立、值得注意的线索

* **错误是单向的**：4 首歌全部"一个歌手被吸进另一个"，从没出现双向混淆。
  这提示某个歌手的某些段落**系统性地更像对方**，而不是随机噪声。
* **错误成段**：《失眠飞行》有一段 **10 行连续错**，《让风告诉你》有 4 行连续。
  段落级现象 → 更像"某些段落的演唱方式/编曲变了"，而不是逐行抖动。
* **和声行反而全对**：x-bg 行 5/5、12/12、3/3 全判对。问题不在和声。

## 7. 候选模型评估结果

### 候选 1：Sony CSL Paris `ssl-singer-identity` —— ❌ **全部 5 个变体拒绝**

专门学"歌手身份表征"的自监督模型（论文 *Singer Identity Representation Learning
using Self-Supervised Techniques*，Torres / Lattner / Richard）。

* 代码 `SonyCSLParis/ssl-singer-identity`（MIT）；权重 `BernardoTorres/singer-identity`
* 骨干 EfficientNet-B0 + 时间平均池化，输出 **1000 维**
* 训练数据 `tencys_vocals` / `ghero_vocals_*` —— **隔离人声轨**，44.1 kHz，
  `nr_samples=176000`（**4 秒**片段）
* 训练增强含 `pitch_shift 1~1.4` + `formant_shift`，目标就是让表征对音高/音区不变
  —— 从动机上确实对准我们的问题

**接口接入方式**（已验证可用）：

| 项 | 结论 |
| --- | --- |
| 依赖 | 走**TorchScript**（官方 `load_model(..., torchscript=True)` = `torch.jit.load`），**完全不需要** torchaudio / nnAudio / torchvision / lightning |
| 输入 | **44.1 kHz**（TorchScript 版源码里写死：`if input_sr != 44100: raise`） |
| 输出 | `(N, 1000)`，官方已 L2 归一化 |
| 速度 | **299× 实时**（5 段 25s 音频 0.08s），跑在 cuda:0 |
| ⚠️ 坑 | `torch.jit.load` 底层是 C++ `fopen`，**绝对路径含中文时找不到文件**（实测：路径里有中文目录就抛 `RuntimeError`）。必须传 BytesIO 或相对路径 |
| ⚠️ 坑 | GPU 上前向有 1e-4 级非确定性（无碍聚类，但别断言"逐位可复现"） |
| ⚠️ 风险 | Python 3.14 下 torch 会告警 `torch.jit.load is not supported in Python 3.14+ and may break` |

**结果（同一评估集、同一跨度、同一 k-means、同一评分）**：

| 条件 | 总体 | 剔版本存疑 |
| --- | --- | --- |
| **基线 CAM++（整行，原始混音）** | **85.0%** | **89.9%** |
| unif-align（整行，原始混音） | 64.4% | 68.8% |
| byol（整行，原始混音） | 64.4% | 67.9% |
| contrastive（整行，原始混音） | 64.4% | 67.9% |
| contrastive-vc（整行，原始混音） | 63.7% | 66.1% |
| vicreg（整行，原始混音） | 58.1% | 57.8% |
| byol（4 秒切片再平均） | 64.4% | 67.9% |
| byol（**隔离人声轨** = 它的训练条件） | 66.2% | 67.9% |

逐歌（取最好的 unif-align）：

| 歌 | 基线 | unif-align | 退化 |
| --- | --- | --- | --- |
| 我不曾忘记 | 97.0% | 81.8% | −15.2 |
| 在出发之前 | 90.6% | 62.5% | −28.1 |
| 让风告诉你 | 84.1% | 63.6% | −20.5 |
| 失眠飞行 | 74.5% | 54.9% | −19.6 |

**四条采用标准（§5 预先约定）全部不通过**：

1. 总体提升 ≥2pp → **−21.1pp**（最好变体 68.8% vs 89.9%）✗
2. 提升不能只来自 1 首歌 → 不适用（没有提升）✗
3. 任一歌下降 ≤3pp → **4 首歌全降 15~28pp** ✗
4. 改善目标错误类型且不损害普通独唱 → 全线崩，且出现新的极端退化
   （《失眠飞行》v2 召回 **0/12**）✗

**结论：拒绝，CAM++ 保留为生产模型。** 生产代码未做任何改动。

**注意事项（避免过度解读）**：

* 这是**一次评估**：4 首歌、160 行、一个评估集。拒绝的置信度较高（差距 21pp、
  4 首歌同向、5 个变体一致、换了输入条件也没救），但"所有歌手嵌入模型都不行"
  这个更强的结论**不成立**——只排除了这一族。
* 我没有测试第五个变体之外的其他架构，也没有做超参搜索（那会在这个小评估集上过拟合）。
* **"同一批歌上挑最好的变体"（unif-align）属于探索性比较，不算独立验证。**
  如果将来要采用某个变体，必须在**新增的、未参与过选择的歌曲**上复验。
* 失败的**最可能原因**（未验证，仅列假设）：训练数据是**独唱**人声轨、按歌手分类
  组织（`group_by_artist`），任务是"识别是哪个歌手"，不是"把一段对唱按行归属到
  两个歌手"；我们的任务里同一行还会混入伴奏与和声，且需要区分的是**同性别、
  同歌曲、同录音条件**下的两个歌手——这比它训练时的判别条件难得多。
  ⚠️ **这是待验证假设，不是结论**。本次实验只能说明"这个模型在我们场景下没用"，
  不能证明"原因是训练目标不匹配"。

## 8. 决策与冻结（2026-10-10）

**决定：保留 CAM++ 作为唯一生产方案；声纹算法研究暂时冻结。**

理由（按证据，不按感觉）：

* 候选族 5 个变体全部明显落后（最好 68.8% vs 基线 89.9%，差 21pp）；
* 换成模型原生 4 秒切片、改用隔离人声轨（它的训练条件）都救不回来；
* 四条采用标准逐条不通过；
* 在这个只有 4 首歌的评估集上继续调参，属于拿有限数据碰运气，不是有证据的改进。

### 冻结期的约束

1. **CAM++ 是唯一生产方案**，`models/campplus/` + `speaker_campplus.py` + `diarize.py`。
2. 实验适配器 `singer_ssl.py` 与权重 `models/singer_identity/`（5×37MB）**留在实验区**，
   **禁止被生产模块引用**。这条由 `selftest.py` 第 21 组强制（扫生产模块源码，
   发现引用即失败），不靠自觉。
3. 候选模型只有在 `tools/eval_diarization.py` 里能选到，CLI / Web UI 都没有入口。
4. 《在出发之前》的 **L7、L12、L13** 不靠算法解决，走编辑台的区间批量改
   （三行里两行连续，选一段点两下即可）。

### 重新立项的门槛（先有证据，再投接入成本）

满足**任一条**才重新评估候选模型：

1. 找到**明确针对以下条件**训练或评估过的模型：
   同歌、同伴奏、**同性别**双人对唱，且任务是"按句归属"而不是"识别歌手是谁"；
2. 积累到新的、可复现的失败案例（例如某类歌稳定分错而现有手段无解）；
3. 现有基线在**新增评估集**上出现明显退化（说明当前方法有我们没看到的边界）。

不满足以上任一条时，不再"为了也许有个模型更好"而搜索候选。

### 评估集可以继续扩

扩评估集本身不受冻结影响，而且**是重新立项的前提**：门槛第 1、3 条都要求更多真值。
真值获取路径见 §1（`index.jsonl` 按标题查 ID → `ghproxy` 拉 `.ttml`），
版本一致性用歌词 2-gram 重合度核验（≥0.75）。
