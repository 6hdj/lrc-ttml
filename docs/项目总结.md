## 1. 项目定位速读

### 1.1 解决什么问题

**输入**：一首歌的音频 + 这份歌词的文本（`.lrc` 或 `.txt`）。
**输出**：一份 XML（TTML），里面**每一个字**都带独立的起止时间，能被 AMLL Player / Apple Music 解析出逐字高亮效果。

痛点在于"逐字时间轴"这件事本身：人工打轴一首 4 分钟的歌要几千次点击。
本项目把这件事**全自动**做掉，人工只负责最后看不准的少数几个字。

### 1.2 产品定位：全自动为主、人工微调为辅

```
【自动阶段｜默认路径】  音频 + 歌词  →  一键生成  →  逐字 TTML + 自检报告
                                        │  生成即建立编辑态（outputs/<id>.edit.json）
                                        ▼
【微调阶段｜少量使用】  编辑台：改少数几个字的时间 / 改几行"谁唱的"  →  保存  →  再导出
```

两条关键的产品判断决定了整体架构：

1. **时间戳必须来自真实音频，不能由语言模型"生成"。**
   大模型会编时间轴且不可复现。所以这里用 ASR 拿到**声学时间戳**，再用强制对齐把歌词钉上去
   （[pipeline.py:1-14](../pipeline.py) 的模块说明明确写了这一点）。
2. **按行锚点比全局猜测可靠得多。** LRC 本身带行级时间戳，把它当锚点分窗口对齐，
   精度远高于"整曲一次对齐"（§7.3）。

### 1.3 与其他方案的本质区别

| 做法 | 时间戳来源 | 优点 | 本项目为何不采用 |
|---|---|---|---|
| 大模型读歌词"编"时间 | 模型幻觉 | 无需音频 | 不可复现、时间凭空捏造 |
| 纯人工打轴（多数编辑器） | 人手点击 | 最准 | 一首歌几千次点击，是本项目要消灭的成本 |
| **ASR + 强制对齐（本项目）** | **真实音频** | 全自动、可复现 | — |

### 1.4 明确的能力边界（先说清楚做不到什么）

| 做不到 | 原因 | 缓解手段 |
|---|---|---|
| 两个人**同时**张嘴的齐唱/和声堆叠 | 声纹只能回答"这一行像谁"，拆交叠人声需要歌手分离模型 | 提示 + 人工，[pipeline.py:815](../pipeline.py) |
| 音色接近的对唱自动分开 | 声纹相似度高于阈值 → 并成一人（实测详见 §8.5） | 元数据艺人数 / `[v1]/[v2]` 标记 / `--agent-from` 复用社区人工标注 |
| 行内换人（同一句两人各半句） | 按行给 agent，行内不切分 | 人工在编辑台处理 |
| Ruby 注音（`tts:ruby`） | 需要额外注音数据源 | 不生成 |
| 逐字翻译 | 需要单独对齐 | 只做逐行翻译 |
| 专有名词大写、语气词取舍等语义判断 | 需要语义理解 | 只做可程序化的 Apple 风格准则（§10.2） |

## 3. 总体技术方案

### 3.1 六阶段流水线

`LyricToTTML.convert()`（[pipeline.py:147](../pipeline.py)）是唯一的编排入口，顺序固定：

```
  音频 + 歌词文本
       │
  [1/6] 解析歌词            LRC 行级时间戳 / 纯文本 / [v1][v2] 标记 / （括号）=背景人声
       │                    + 可选的 Apple 风格规范化、可选的人声分离
  [2/6] 语音识别            faster-whisper，带 LRC 时**按乐句切片**并用该句歌词做提示词
       │
  [3/6] 强制对齐            歌词按字切分 ⟷ 识别结果做单调 DP 对齐（同音字/错字/漏字容错）
       │
  [4/6] 低匹配率行精修      只重听那一行的时间窗，重新对齐；有第二条音轨时两轨都试、取更准的
       │
  [ 5 ] 后处理              丢开头没唱的信息行 → 停顿空格 → 演唱者归属 → 消音词检测 → 翻译
       │
  [6/6] 输出 + 自检         生成 TTML → 确定性自检 → **再用真 AMLL 解析器验"播放器里能不能显示"**
```

### 3.2 五个贯穿全局的设计决策

**(1) 一切时间戳来自音频，且"可解释"。**
`AlignedLine` / `Unit` 保留了 `matched`（是否真的匹配上 ASR）和 `prob`（置信度），
未匹配的字是**插值**补出来的（[matcher.py:584](../matcher.py)）。
这两个字段一路传到编辑台，直接变成 UI 上的"灰色/黄色/红色"提示（§12.2）——
让用户**看得见哪里不可信**，而不是给一个看起来很整齐但暗中瞎猜的结果。

**(2) 主唱层与背景层严格分开处理。**
`Unit.is_bg` 标记背景人声；所有时间归一化都**按层分别做**
（[matcher.py:706](../matcher.py)、[ttml_normalize.py:32-36](../ttml_normalize.py)）。
因为 AMLL 规范允许**和声与主唱时间重叠**（"因混音而使时间重叠的情况除外"），
把它和主唱压在一起会写出规范允许但被误判的坏文件。

**(3) 时间按"文本顺序"排，不按时间排。**
这是被反复强调的不变量（[matcher.py:704-710](../matcher.py)）。
输出时 `<span>` 是按文本顺序写的；如果时间顺序与文本顺序不一致，播放时字会跳来跳去。

**(4) 每个"容错"都要有对应的"验证"。**
项目里几乎每个宽松处理都配了一个检查：
切片识别可能有提示词失效 → `_looks_degenerate` + 无提示词重识别（[pipeline.py:447](../pipeline.py)）；
声纹可能判错 → `uncertain` 行提示 + 编辑台批量改（[diarize.py:247-257](../diarize.py)）；
自己的校验器查不出语义问题 → 上真 AMLL 解析器（[pipeline.py:324-353](../pipeline.py)）。

**(5) 绝不因为附加功能把主流程搞挂。**
所有可选增强（人声分离、声纹、AMLL 解析器验证）都包在 `try/except` 里，
失败只写一条 note 并**继续用降级路径**
（[pipeline.py:352](../pipeline.py)、[pipeline.py:636-639](../pipeline.py)）。

## 4. 六阶段流水线逐段拆解

### 4.1 阶段 1：解析歌词（[pipeline.py:169-198](../pipeline.py)）

```
parse_lyrics(text)        纯文本 or LRC → List[LyricLine]
detect_agent_switch()     套用 [v1]/[v2]/[和声]… 标记
_is_credit_line() 过滤    "作词/作曲/录音师…" 等制作人员行（可关）
_apply_style()            可选：Apple 风格规范化
```

**制作人员行的识别用了"正则 + 结构特征"双保险**（[pipeline.py:51-64](../pipeline.py)）：
关键词表（`作词|作曲|录音师|…`，含英文）覆盖已知词，
但关键词永远穷举不完，所以加了一条**结构判据**：前 30 秒内、形如 `标签：内容` 的短行，
或形如 `歌名 - 歌手A&歌手B` 的标题行，也算信息行。

**还有一道"事后"过滤**：[pipeline.py:577](../pipeline.py) `_drop_leading_unmatched()`
丢掉**开头连续、字级匹配率为 0** 的行。依据很硬：这些行根本没被唱出来，所以匹配率必然是 0。

### 4.2 阶段 2：语音识别（[pipeline.py:207-227](../pipeline.py)）

两条路径，由"有没有 LRC 行级时间戳"决定：

| 条件 | 路径 | 做法 |
|---|---|---|
| 有 LRC 锚点 + `chunked`（默认） | **按乐句切片识别** | 把连续几行合成一个"乐句"，只转写那段时间窗，**并用该段歌词本身做 `initial_prompt`** |
| 无锚点 / `--no-chunked` | 整曲一次识别 | 用歌名+歌手+前 6 行歌词做提示词 |

切片识别的收益很大（[pipeline.py:402-406](../pipeline.py) 的实测注记）：
**整曲一次识别会整段漏掉短句（尤其背景和声）**；切片+歌词提示词后字级时间轴几乎完全正确。

### 4.3 阶段 3：强制对齐（[pipeline.py:229-232](../pipeline.py) → §7）

### 4.4 阶段 4：低匹配率行精修（[pipeline.py:234-252](../pipeline.py)）

只对匹配率低于阈值（默认 0.6）的行，**重听那一行的时间窗**再对齐一次，取更好的结果。

**精修带双轨复核**（[pipeline.py:483-561](../pipeline.py)）：
若同时有原混音和 Demucs 人声轨，就把阈值抬到 0.95，
**只要不是近乎满分，两条轨都重新识别一遍，取匹配率更高的那个**。
理由是实测两条轨各有胜负 —— 分离整体更好，但个别行反而原轨更准
（比例见 README「人声分离」表）。

### 4.5 阶段 5：后处理

按顺序：丢开头未唱行 → 停顿空格 → **演唱者归属** → 消音词检测 → 翻译挂载。

停顿空格（[pipeline.py:827](../pipeline.py)）依据 AMLL 习惯：
字与字之间停顿超过 `--pause-space` 秒时，给前一个字补一个空格（AMLL 用空格表示停顿）。

## 5. 音频输入层

### 5.1 设备探测：为什么不能信 `torch.cuda`

`WhisperASR._detect_device()`（[asr.py:79-97](../asr.py)）**先问 ctranslate2，再问 torch**：

```python
import ctranslate2
if ctranslate2.get_cuda_device_count() > 0: return "cuda"
...
import torch
if torch.cuda.is_available(): return "cuda"
```

原因写在注释里：本机的 torch 可能是 **CPU-only 版**（`2.x.x+cpu`），
此时 `torch.cuda.is_available()` 是 `False`，**但 ctranslate2 仍然能用显卡**。
只看 torch 会白白浪费 GPU。

`compute_type` 随之自动选择：CUDA → `float16`，CPU → `int8`（[asr.py:74-75](../asr.py)）。

### 5.2 CUDA DLL 注册（[asr.py:99-124](../asr.py)）

ctranslate2 的 CUDA 版需要 `cublas64_12.dll` / `cudnn*64_9.dll`。
pip 装的 `nvidia-*-cu12` 把这些放在 `site-packages/nvidia/<lib>/bin`，
Windows 上必须显式注册：

```python
os.add_dll_directory(d)                     # Python 3.8+
os.environ["PATH"] = d + os.pathsep + os.environ["PATH"]
```

**这是为了不改系统 PATH 就能用 GPU。**

### 5.3 本地模型优先（[asr.py:126-138](../asr.py)）

`resolve_model_path()` 先找本地 HF 缓存里的 snapshot（找 `model.bin`），
找不到才交给 faster-whisper 联网下载。**本地已有缓存时全程离线可用。**

### 5.4 切片识别的窗口怎么算（[pipeline.py:375-400](../pipeline.py)）

`_line_span()` 返回每行的 `(开始, 合理演唱结束)`：

- 开始 = LRC 行时间；
- 结束 = 按字数估的上限 `max(1.4, 0.75*字数 + 1.0)`，并且**被下一行开始时间截断**
  （LRC 的行结束常常就是下一行开始，中间可能是大段间奏，不能整段送进识别）。

**一个踩过的坑**：合并了背景和声的行**不能**按"下一行开始"截断
（[pipeline.py:387-393](../pipeline.py)）。因为 LRC 里和声与下一句常常只差 0.2 秒
（和声 `[03:32.87]` vs 下一句 `[03:33.09]`），真人和声会一直唱到下一句开始之后。
按下一行截断的话，几个和声字会被硬挤进 0.2 秒里 → 时间戳重叠的坏文件。

### 5.5 乐句怎么切（[pipeline.py:412-427](../pipeline.py)）

从第一行开始累积，遇到任一条件就断开：

| 条件 | 阈值 | 含义 |
|---|---|---|
| `chunk_gap` | 2.5 s | 行与行之间**间隔**太久（中间是间奏） |
| `chunk_max_span` | 7.0 s | 相邻两行**开始时间**相差太远（中间多半是间奏） |
| `chunk_max_seconds` | 22.0 s | 单个乐句总时长上限 |
| `chunk_max_lines` | 10 行 | 单个乐句行数上限 |

### 5.6 提示词工程：一个反直觉的坑（[pipeline.py:435-438](../pipeline.py)）

```python
# 提示词只放歌词本身。注意不要在开头加「。」之类的分隔符：
# 实测（large-v3, CPU）提示词以标点开头时，whisper 会把整段歌词
# 合并成几个长达 9 秒的"词"，字级时间轴直接失效。
prompt = "\n".join(lines[k].text for k in chunk)[:500]
```

### 5.7 退化检测与兜底（[pipeline.py:446-468](../pipeline.py)）

`_looks_degenerate()` 判据（任一命中即认为这段识别崩了）：

```python
len(words) < max(3, int(0.35 * expect_chars))   # 词数太少（相对期望字数）
dur / len(words) > 1.2                          # 平均"词"时长过长
max(w.end - w.start) > 4.0                      # 有单个"词"超过 4 秒
```

崩了就用**不带提示词**的方式重识别一次，谁的结果更合理用谁。
注释里的理由：提示词约束太强时 whisper 会把整段歌词压成几个超长"词"。

## 6. 歌词解析层（`preprocess.py`）

### 6.1 数据结构

```python
@dataclass
class LyricLine:                      # preprocess.py:18
    text: str
    tokens: List[WordToken]
    line_start / line_end: Optional[float]   # LRC 行级时间戳
    agent: str = "v1"                 # 演唱者
    role: str = ""                    # Apple 扩展角色 x-duet-a / x-narration
    manual_agent: bool = False        # 来自歌词里手写的标记（手写优先）
    manual_background: bool = False   # [和声]/[bg] 标出来的整行背景
    paragraph: int = 0                # 源歌词空行分段（用于分 <div>）
```

### 6.2 分词：中文按字、英文按词、标点吸附（[preprocess.py:43-96](../preprocess.py)）

`tokenize_chinese()` 逐字符扫描，产出 `WordToken`：

| 字符 | 处理 |
|---|---|
| `（([【` / `）)]】` | 切换 `in_background`，括号本身**不产出 token**（它只是标记） |
| 空格 | 跳过 |
| `，。！？、,.!?~…—-` | 标点 token（`is_punctuation=True`，并继承背景标记） |
| CJK（`\u4e00-\u9fff`、`\u3040-\u30ff`） | **按字**拆 |
| ASCII 字母数字 | **按词**读（含 `'` `’`） |
| 其他 | 单字符 token |

注意：**对齐用的 `Unit` 与这里的 `WordToken` 是两套结构**。
`matcher.scan_line()` 是更精细的一套（标点作为 `leading/trailing` 吸附到相邻字上，
见 §7.1），`WordToken` 主要用于背景判定。

### 6.3 整行背景人声必须并进主唱行（[preprocess.py:110-179](../preprocess.py)）

**这是本项目最重要的格式修复之一。**

AMLL/Apple 的数据模型里，背景人声是**某一行的子内容**（`<p>` 内的 `<span ttm:role="x-bg">`），
不是独立一行。如果让它单独成行，生成的 `<p>` 里只有 `x-bg`，
而 AMLL 解析器在 `case Values.RoleBg` 时**不把背景人声计入该行 fullText**
（见 `amll-dev/applemusic-like-lyrics` 的 `packages/ttml/src/parser.ts`），
于是这一行主歌词为空、`words` 为空 → **播放器里背景人声不显示**。

合并规则（[preprocess.py:120-123](../preprocess.py)）：

| 情况 | 处理 |
|---|---|
| 背景行在**主唱行之后** | 追加到上一主唱行 token 末尾（主唱先唱、和声在后） |
| 背景行在**主唱行之前** | 并入下一主唱行，token 放最前面 |
| 找不到邻居 / 时间跨度 > `BG_MERGE_MAX_SPAN`（12 s） | 保持独立行 |

`[和声]`/`[bg]` 标出来的行原文可能没括号，会**补一对半角括号**
（[preprocess.py:128-130](../preprocess.py)），规范 §7.3 也要求用半角括号包裹。

### 6.4 标记必须在合并之前剥掉（[preprocess.py:181-212](../preprocess.py) 注释）

**踩过的坑**：`[v1]（一路践行）` 这种和声行，如果先合并再剥标记，
分词时 `v1` 也会被判成背景 token → 整行被并进主唱行；
等合并完再剥就晚了，`[v1]` 已经在行**中间**，行首匹配不到，
最后渲染成 `(v1一路践行)`。所以 `_strip_marker()` 在 `parse_lyrics()` 里**逐行先剥**，
`detect_agent_switch()` 再沿用已剥出来的 agent/role。

### 6.5 标记 → 规范语义（`detect_agent_switch()`，[preprocess.py:306](../preprocess.py)）

| 歌词里的标记 | 变成什么 | 依据 |
|---|---|---|
| `[v1]` `[男声]` `[主唱]` | `<p ttm:agent="v1">` | AMLL §7.2 对唱 = 不同 `ttm:agent` |
| `[v2]` `[女声]` `[对唱]` | `<p ttm:agent="v2">` | 左右分栏靠这个触发 |
| `[合唱]` `[齐唱]` `[group]` | `ttm:agent="v1000"`，head 里 `type="group"` | AMLL §4.1 group 固定 v1000 |
| `[和声]` `[bg]` `[伴唱]` | **不是 agent**：整行成为 `x-bg` 层并进主唱行 | AMLL §7.3 背景是行的子内容 |
| `[旁白]` `[独白]` | `ttm:agent="v3"` + `x-narration` | AMLL §4.1 + Apple 扩展 |

`ttm:name` **只给 person/character/organization**——
`group`/`other` 不是某位歌手，按顺序硬套会把歌手名安到合唱上。

### 6.6 编码探测（`textread.py`）

**为什么需要**：中文 Windows 上的 `.lrc` 大量是 **GBK/GB18030**，
写死 `encoding="utf-8-sig"` 会直接抛
`UnicodeDecodeError: 'utf-8' codec can't decode byte 0xce ...`，
用户上传一个 GBK 的歌词就整个转换失败 —— 这是纯工程问题，不该让用户去转码。

策略顺序（[textread.py:8-20](../textread.py)、[textread.py:81-98](../textread.py)）：

```
1) BOM 是铁证     utf-8-sig / utf-16 / utf-32 有 BOM 直接采信
                  （无 BOM 的 utf-16 一律不猜 —— 它能把任意字节解成"看起来正常"的乱码）
2) 严格 UTF-8     能解开就是它（严格通过是很强的证据）
3) gb18030        GBK/GB2312 的超集，覆盖简体老文件
4) 兜底           utf-8 + errors="replace"，并标记为"可能损坏"
```

**已知边界**：Big5（繁体）会被 gb18030 **静默**误解成乱码（gb18030 几乎不抛异常）。
所以解完还要过一遍 `_looks_broken()` 合理性检查（[textread.py:40-78](../textread.py)）：
出现 U+FFFD、非法控制字符、或"期望字符占比 < 80%"就标 `dirty`，
**让调用方提示用户，而不是闷着**。

`read_text_best_effort()` 返回 `(文本, 编码, 是否可疑)`，
调用方把编码写进日志（[web_server.py:292-297](../web_server.py)）。

## 7. 对齐核心（`matcher.py`）

这是整个项目的技术心脏。要解决的问题是：
**给定一行歌词（N 个字）和一段时间窗内的 ASR 输出（M 个词/字，含错字、漏字、多字、幻觉词），
求"哪个字对应哪段时间"的最优单调匹配。**

### 7.1 第一步：把歌词切成"对齐单元"（`scan_line()`，[matcher.py:125](../matcher.py)）

```
Unit:
  core      用于匹配的文本（汉字单字 / 英文单词）
  index     行内序号（后处理依赖它，勿按时间排）
  leading   前置标点/空格
  trailing  后置标点/空格
  is_bg     是否背景人声
  start/end/prob/matched/muted
```

关键设计：**标点不作为独立对齐单元**（[matcher.py:89-93](../matcher.py) 的 `_is_attachable()`：
Unicode 类别以 `P`（标点）或 `S`（符号）开头，且不是括号）。
它们被**吸附到相邻的字**上（`leading`/`trailing`），
因为 ASR 不会给标点独立的时间戳，让标点参与 DP 只会制造噪声。

空格的保留规则很细（[matcher.py:137-142](../matcher.py)）：
中文之间的空格**不保留**（AMLL 中文歌词不用空格），
但中英混排/英文单词之间的空格**必须保留**。

### 7.2 相似度函数（`similarity()`，[matcher.py:234-269](../matcher.py)）

这是 DP 的目标函数，取值直接决定对齐取舍：

| 情形 | 分数 | 理由 |
|---|---|---|
| 完全相同 | `1.0` | — |
| 仅大小写不同 | `0.97` | — |
| **CJK 同音字**（拼音完全相同） | `0.85` | 极可能只是识别/用字差异 |
| CJK 声母或韵母相同 | `0.5` | — |
| CJK 不同汉字（同为汉字） | `0.4` | 位置信息仍然有效（识别错字） |
| 两个不同的拉丁字符 | `0.25` | — |
| **汉字 vs 拉丁字母** | **`-0.2`** | 基本不可能是同一个音 |
| 多字单元：一方包含另一方 | `0.6` | 英文词/多字识别结果 |
| 多字单元：其他 | `0.3 + 0.4 * 相同位置占比` | — |

**负分是关键设计**（[matcher.py:237-239](../matcher.py) 注释）：
识别结果里经常混进"幻觉词"（把音乐识别成 `issippi`、把和声识别成"优优独播剧场"）。
跨语种/完全不相关的配对给**负分**，DP 就会选择"丢弃这个词"，
**而不是把歌词硬贴到它上面**。

拼音来自 `pypinyin`（[matcher.py:36-53](../matcher.py)），带缓存；没装则退化为纯字面比较。

### 7.3 动态规划（`align_sequences()`，[matcher.py:281-327](../matcher.py)）

标准 Needleman–Wunsch 结构，但**线性 gap 罚分**：

```python
GAP_OPEN = -0.5          # 每跳过一个单元扣 0.5
EARLY_BONUS = 1e-4       # 极小的时间偏好：同分时优先匹配更早出现的识别结果
```

`dp[i][j] = max(dp[i-1][j-1] + pair(i-1,j-1),    # 配对
                dp[i-1][j] + GAP_OPEN,            # 歌词跳过
                dp[i][j-1] + GAP_OPEN)`           # 识别结果跳过

**为什么用线性 gap 而不是仿射 gap**（[matcher.py:284](../matcher.py) 注释）：
"对小规模序列足够且没有 O(n³) 风险"。复杂度 `O(n·m)`。

**`EARLY_BONUS` 解决一个具体问题**（[matcher.py:276-278](../matcher.py)）：
whisper 复读整句时（同一句识别两遍），希望对齐到**先唱的那一遍**，
而不是被推到后面。加一个极小的、随 `j` 递减的奖励即可破平局。

**回溯时必须带容差比较**（[matcher.py:319-326](../matcher.py)）：
用 `< 1e-9` 而不是 `==` 判断路径，否则浮点误差会让回溯走错路。

### 7.4 两种对齐模式（`LyricMatcher.align()`，[matcher.py:394](../matcher.py)）

**(a) 有 LRC 锚点：分窗口对齐**（推荐路径）

```
1. 给每行算一个目标时间窗 (start, end)
   - start = LRC 行时间
   - end   = 按字数估 max(2.0, 0.9*字数 + 1.5)，且被下一行开始时间截断
2. _bucket_by_window()  把 ASR 单元按窗口分桶
3. 逐行 _align_line()   行内做 DP + 插值
4. _finalize_line()     收敛窗口、消除重叠、保证 begin<end
```

**分桶时窗口故意允许重叠**（[matcher.py:487-504](../matcher.py)）：
每个窗口向两边各扩 `window_pad=0.35s`。
原因：**whisper 的字级时间戳常常比 LRC 行时间早 0.1~0.3 秒**，
硬切会让每行第一个字掉进上一行的桶里。多出来的单元由 DP 的 gap 罚分自然丢弃。

**(b) 无锚点（纯文本）：全曲全局对齐**

把**所有行的单元拼成一条长序列**，对整曲 ASR 做一次 DP，
然后按行拆开、逐行插值（[matcher.py:453-476](../matcher.py)）。
精度低于 (a)，所以纯文本输入时会提示用户"建议提供 LRC"。

### 7.5 可信度判据与退化为"按比例分配"

DP 只关心总分，**有时会把歌词"贴"到明显无关的幻觉词上**（贴上去的收益比丢弃两个单元更高）。
所以配了两道过滤：

**(1) 逐对阈值过滤**（`_apply_mapping()`，[matcher.py:506-528](../matcher.py)）：
相似度低于 `min_match_score=0.2` 的配对一律当作未匹配，交给插值 —— 结果反而更稳。

**(2) 整行可信度判据**（`_trustworthy()`，[matcher.py:547](../matcher.py)）：
一行如果整体不像话，就整行退化为 `_proportional()`
（在行窗口内**按字数均分**，[matcher.py:567](../matcher.py)）。
退化的场景有两类：

- 该窗口内**没有识别到任何东西** → 直接均分（[matcher.py:534-537](../matcher.py)）；
- 有识别结果但不可信 → 弃用 DP 结果，均分。

**这是刻意的工程取舍**：宁可给出"均匀但诚实"的估计，也不给出"看起来精确但乱贴"的时间轴。

### 7.6 未匹配字怎么补时间（`_interpolate()`，[matcher.py:584](../matcher.py)）

DP 没匹配上的字需要在相邻已匹配字之间补时间：

- 前有已匹配字、后有已匹配字 → 在两者之间**按字数均分**；
- 只有前面（行尾漏字）→ 从上一个字结束时间往后按步长铺；
- 全行都没匹配上 → 由 `_proportional()` 兜底。

**这些字会被标记为 `matched=False`**，一路传到编辑台显示为**红色** ——
它们是最该人工看一眼的位置（README 里"某个字只有 0.06 秒"的 FAQ 说的就是这种情况）。

### 7.7 三道后处理（保证输出合法）

行内后处理与跨行后处理都委托给 `ttml_normalize` 的纯函数，
**生成链路与编辑链路共用同一份算法**（[matcher.py:26](../matcher.py) 导入、
[matcher.py:706-733](../matcher.py) 三个薄封装）：

| 顺序 | 函数 | 职责 |
|---|---|---|
| 1 | `_finalize_line()`（[matcher.py:670](../matcher.py)） | 按层归一化 + 由 span 反推行的 begin/end |
| 2 | `_fix_cross_line_overlaps()` | 同一演唱者的相邻行不得重叠 |
| 3 | `_clamp_units_into_lines()` | 任何字必须落在所属行的区间内，且按文本顺序单调 |

**为什么"同一个 agent 的行不能重叠，不同 agent 可以"**：
AMLL 规范 §6-4 如此规定，而且 Apple Music 的**左右分栏**正是靠"两个 agent 的行在时间上可以交叠"来实现对唱效果。

**规则 13（AGENTS.md）值得单独记**：行尾装不下时**先整组回推**，仍装不下就**让行尾长出去**；
**绝不能把多个字压进同一个 `[end-min, end]` 窗口**（那样同层字时间会重叠）。
这个坑真实踩过，最终由 `ttml_normalize.clamp_units_into_line` 兜住 ——
`spare = group[0].start - begin`（前面还能往前让出多少），
`shift = -min(overflow, spare)`（能回推多少就回推多少），
回推后仍溢出才让 `end = group[-1].end`（[ttml_normalize.py:184-193](../ttml_normalize.py)）。
docstring 里留着事故记录："早先的实现就是'压窗口'，结果同一层出现多个 span 时间完全相同，
校验器报'字时间重叠'、播放器里字会闪"（[ttml_normalize.py:162-164](../ttml_normalize.py)）。

## 8. 演唱者分声部

### 8.1 三层优先级的归属决策（[pipeline.py:258-273](../pipeline.py)）

```
① 手写标记 [v1]/[v2]       → 最高优先级，直接用（manual_agent=True 时跳过自动分段）
② --agent-from 参考 TTML   → 复用社区已有人工标注（最可靠的自动化路径）
③ CAM++ 声纹自动聚类        → 兜底
```

③ 内部还要先决定"分几瓣"（见 §8.5）。

### 8.2 声纹提取：整行一次前向（`line_embedding()`，[diarize.py:61](../diarize.py)）

用 CAM++ 提每行的 192 维说话人向量。**关键：`mode="whole"`（默认）= 整行一次前向**，
而不是把行切成 1.5 s 小窗分别提再平均。

**这个改动是被人工真值逼出来的**（[diarize.py:69-83](../diarize.py) 注释里的实测表，
以《在出发之前》32 行为基准、强判 2 簇与人工真值的一致率）：

| 做法 | 一致率 |
|---|---|
| 整行 embedding（**原始混音**） | **90.6%** |
| 整行 embedding（Demucs 人声轨） | 53.1% |
| 窗口平均（不论哪条音频） | **50.0%**（= 瞎猜） |

原因：一行之内音高/音区变化很大，1.5 s 窗口的 CAM++ 向量本身就不稳，
**平均之后身份方向相互抵消**。

还有一个**反着来的细节**：旧实现会"丢掉低能量窗口"（本意是丢掉静音），
但如果用的是**原始混音**，低能量窗口恰恰是伴奏最轻、人声最清楚的；
丢掉之后留下的反而是**伴奏最响**的窗口 —— 等于专门挑最不像人声的片段去提声纹。

### 8.3 声纹必须用原始混音，不能用 Demucs 分离轨

这条也很反直觉（[pipeline.py:267-272](../pipeline.py)）：
Demucs 为了分离人声会把**共振峰细节平滑掉**，而共振峰恰恰是身份线索。
实测用分离轨做声纹，一致率从 93.9% 掉到 54.5%（约 37 个点）。

所以 `ConvertOptions.diarize_on` 默认 `"mix"`（[pipeline.py:112](../pipeline.py)），
分离轨只用于**识别**（whisper 更喜欢干净人声），不用于**声纹**。

### 8.4 聚类与人工兜底

- 强制人数时用 **k-means**（[diarize.py:219-222](../diarize.py)），
  实测比旧的"平均连接贪心 `_force_k`"好 34 个点（后者会退化成 31/1）；
- 不强制时用平均连接层次聚类 + 小簇合并（[diarize.py:223-231](../diarize.py)）；
- 簇数超过 `max_singers=6` 时取最大的几个簇（[diarize.py:233-237](../diarize.py)）。

**`uncertain` 只当弱提示**（[diarize.py:247-257](../diarize.py)）：
"到两个簇心的余量最小 = 两个人都像"。但实测本曲 3 个错行的余量排名是 1/32、13/32、23/32 ——
要全抓得列 24 行（**75% 误报**）。所以调用方只列最小的 3 行，并明说参考价值有限
（[pipeline.py:820-823](../pipeline.py)）。

### 8.5 一个重要的负面结论：分几瓣，音频内部判不出来

`diarize()` 的文档注释（[diarize.py:188-199](../diarize.py)）记录了三种内部判据**全部失败**的实测：

| 判据 | 结果 |
|---|---|
| 平均连接阈值扫描 | 最好 59.4% |
| "分离质量"（簇内-簇间 gap / silhouette / inertia 降幅） | **单人歌强判 2 簇反而比真对唱更高**（+0.254 vs +0.127）—— 它衡量的是"k-means 分得好不好"，不是"是不是两个人" |
| 成对相似度的 BIC 双峰检验 | 真对唱判 1 个成分、单人歌判 2 个（**完全反了**） |

所以规则变成（[pipeline.py:775-787](../pipeline.py)）：

- 元数据写了 **≥2 位艺人** → 按 2 个声部聚类；
- 开了 `--auto-agents` 但没给艺人数 → **也按 2 个声部聚类**，
  并提示"若其实是单人演唱，用 `--split-singers 1`"
  （注释解释了为什么：自动判簇几乎永远返回 1 个声部，等于这个开关没接上）；
- 用户可用 `[v1]/[v2]` 标记或 `--split-singers N` 覆盖。

### 8.6 对唱分栏的"最容易以为有其实没有"

`duet_hint()`（[pipeline.py:67-80](../pipeline.py)）会检测这种情况：
**元数据有多位艺人，但声纹判定为单人 → 全曲只有 `v1` → Apple Music 绝对不会左右分栏。**
此时给出可操作提示（加标记 / `--split-singers 2`）。

这是设计上刻意做的一个"防误判"提示，因为它是本工具最容易让人误以为成功的地方。

### 8.7 无模型时的退化路径

CAM++ 权重缺失时退回 `_diarize_acoustic()`（[diarize.py:503](../diarize.py)），
用**自实现的 MFCC / f0 / 谱质心**等声学特征 + 聚类（[diarize.py:399-476](../diarize.py)），
并在 `DiarizeResult.method` 标注 `acoustic`、明确低置信度。

`speaker_campplus.py` 是**自实现的 Kaldi 风格 fbank 前端**（[speaker_campplus.py:80-101](../speaker_campplus.py)）：
80 维 log-mel，与 Kaldi 的 `snip_edges=True` 一致，
含 dither、去直流、预加重（0.97）、Hamming 窗、512 点 rfft、mel 滤波、取 log。
CAM++ 网络定义从从 funasr wheel 取出的 `models/campplus_src/model.py` 加载
（[speaker_campplus.py:107-135](../speaker_campplus.py)），
**只依赖 torch + numpy**，不需要装 funasr。

## 9. 人声分离（`separate.py` + `pipeline._separate_vocals`）

### 9.1 做法

Demucs `htdemucs` 把混音拆成人声/伴奏，取 vocals 轨
（[separate.py:101-132](../separate.py)）：

```
读取音频（重采样到模型采样率、多声道）
  → 按参考声道做标准化 (wav - mean) / std
  → apply_model(..., split=True, overlap=0.25, shifts=1)
  → 反标准化
  → 取 model.sources.index("vocals")
  → julius 重采样到 16kHz → 单声道 → 写 wav
```

**输出固定 16 kHz 单声道**，可以直接喂给 whisper 和声纹模型，不需要再转码。

### 9.2 结果缓存与复用（[pipeline.py](../pipeline.py) 的 `vocals_cache_path`）

缓存到 `outputs/<歌名>.<demucs模型>.vocals.wav`，命中条件有两个：
文件存在、**且人声轨比原音频更新**（`getmtime` 比较）、且大小 > 1 KB。
分离很费时间，同一首歌重复跑直接复用。

> **缓存键必须带模型名**（2026-10-10 修）：复用判据只看得到文件名，所以若不同模型的产物
> 共用 `<歌名>.vocals.wav`，换 `--demucs-model` 时会**静默复用**上一个模型切出来的人声轨 ——
> 用户以为换了模型（比如换成更准的 `htdemucs_ft`），实际拿到的还是旧结果，且没有任何提示。
> 现在文件名里带模型名（[pipeline.py:131](../pipeline.py)），换模型必然换缓存文件。

### 9.3 分离不是万能的：双轨复核

README 的实测表说得很清楚：**仅分离**让《在出发之前》从 94.0% 提到 95.5%，
但让《它像一颗》里 3 行**反而变差**（98.1% → 97.2%）。

所以加了双轨复核（[pipeline.py:234-241](../pipeline.py)）：
一旦开了分离，精修阈值自动抬到 **0.95** ——
只要某一行不是近乎满分，**人声轨和原始混音都会重新识别一遍，取匹配率更高的那个**。

### 9.4 它解决不了什么

Demucs 只分离"人声 / 伴奏"，**不分离"歌手 A / 歌手 B"**。
人声轨里两个人还是混在一起。
要真正拆开需要歌手分离模型（UVR karaoke 系列、MelBand-Roformer 等）。

## 10. 输出与验证

### 10.1 TTML 生成（`ttml_writer.py`）

`TTMLWriter`（[ttml_writer.py:199](../ttml_writer.py)）的构造参数就是输出形态的开关：
`mode` / `markers` / `line_id` / `translation_style` / `time_format` / `song_part` /
`inline_translation_lang` / `bg_layout` / `agent_types`。

`write()`（[ttml_writer.py:265](../ttml_writer.py)）接收 `Sequence[AlignedLine]`，
按 `<head><metadata>` → `<body dur>` → `<div>` → `<p>` → `<span>` 逐层生成。

**时间表达式层**（不可回退的实现，规范文档 §6.1）：

| 函数 | 职责 |
|---|---|
| `format_time(seconds, style)`（[:102](../ttml_writer.py)） | `clock` → `HH:MM:SS.mmm`（W3C 合法）；`mmss`/`seconds` 是 AMLL 私有宽松写法 |
| `is_valid_time_expression()`（[:130](../ttml_writer.py)） | TTML1 §10.3.1 严格校验（含 offset-time 单位、帧段限制） |
| `is_amll_relaxed_time()`（[:147](../ttml_writer.py)） | 识别 AMLL 宽松写法（用于降级为警告） |
| `parse_time()`（[:155](../ttml_writer.py)） | 读回：`hh:mm:ss[.fff]` / `hh:mm:ss:ff` / `12.5s` / `250ms` / 兼容宽松写法 |

**XML 安全**：所有文本/属性都必须走 `xml_safe()` / `_esc()` / `_attr()`
（[ttml_writer.py:85-100](../ttml_writer.py)），它们会**先清掉 XML 1.0 非法字符再转义**。
歌词里混进非法控制字符会让播放器直接解析失败，这是硬性要求。

**区间归一化**（保证 `span ⊆ p ⊆ div ⊆ body@dur`）：
`_line_interval()`（[:486](../ttml_writer.py)）由 span 反推行的 `p` 区间；
`_unit_interval()`（[:497](../ttml_writer.py)）把 span 夹进 `p` 区间，零时长撑到 1 ms。

**段落划分**：[ttml_writer.py:430-485](../ttml_writer.py) 的 `_split_sections()` /
`_label_sections()`：`--mode apple` 时按静默间隔切 `<div itunes:songPart="Verse|Chorus">`，
重复段落标 `Chorus`。注意**不猜段落名**（README 明确说自动切出来的只是按停顿猜的，建议人工确认）。

**一个已知缺陷**：便利函数 `write_ttml()`（[ttml_writer.py:583](../ttml_writer.py)）
只取 `mode`，其余构造期参数（`markers`/`line_id`/`time_format`/`bg_layout` 等）既不会被
"静默忽略"、也不会生效 —— 它们被转发给 `write()`，而 `write()` 没有这些形参，
**会直接抛 `TypeError`**（构造参数在 [ttml_writer.py:200-211](../ttml_writer.py)，
`write()` 形参在 [:265-280](../ttml_writer.py)，两组名字零交集）。
仓库里 `write_ttml` **没有任何调用点**，属潜伏陷阱。
所以回写一律直接构造 `TTMLWriter`（`ttml_reader.make_writer` 就是这么做的）。

### 10.2 Apple 歌词风格准则（`lyric_style.py`）

**默认不改动歌词原文**（`--style keep`）；需要规范化时用 `--style apple`，
且**所有改动都会逐条列出来**（`StyleReport.detail()`，[lyric_style.py:75](../lyric_style.py)）。

实现的准则：

| 准则 | 实现 | 开关 |
|---|---|---|
| 行尾不得用句号/逗号 | `strip_trailing_punct()`（[:85](../lyric_style.py)）去掉行尾 `.,。，`，保留 `! ? "` | `--style apple` |
| 英文行首词大写；括号内首词大写 | `capitalize_english()`（[:93](../lyric_style.py)）**只做大写、不做小写**（不破坏 NASA / iPhone） | `--style apple` |
| 消音屏蔽的词用星号替换 | `_detect_muted()`（[pipeline.py:665](../pipeline.py)）：**该字时间窗里既没能量也没基频** → `****` | `--detect-muted` |
| 儿童适宜版本屏蔽脏话 | `mask_profanity()`（[:122](../lyric_style.py)）内置中英文屏蔽词表 | `--explicit-policy mask` |
| 儿童不宜版本照实抄录 | 默认一字不改 | 默认 |
| 背景人声单独一行 | **在 TTML 里表示为同一 `<p>` 内的 `x-bg` 层**，不是独立 `<p>` | 自动（§6.3） |

**明确做不到的**（README 列出）：专有名词/品牌名大写、`ooh`/`ah` 该不该录、电脑音效要不要抄、
印度语系拉丁转写 —— 这些需要语义理解，工具不做。

### 10.3 自检（`ttml_check.py`）

确定性、无网络、无大模型。`check_ttml(text, strict=True)`（[ttml_check.py:75](../ttml_check.py)）
回答两个问题：**格式合法吗？时间轴合理吗？**

检查项（按代码顺序）：

| 类别 | 检查 |
|---|---|
| 文件层 | BOM 检测、XML 可解析 |
| 根元素 | `xmlns`、`xml:lang`（BCP-47 格式）、`itunes:timing` 取值 |
| 结构 | `<head>` / `<body>` / `<div>` 存在性 |
| 元数据 | `<ttm:agent>` 有 `xml:id`；`amll:meta` 必填项（musicName/artists/album）；至少一个平台 ID；翻译 `<text for>` 指向存在的行；head 与行内翻译重复告警 |
| 行级 | `itunes:key`/`xml:id` 存在与格式（`L\d+`）；`begin < end`；行区间不越出所在 `<div>`；引用的 agent 已定义 |
| **致命写法** | **未知 role 的包装 span**（[:267-279](../ttml_check.py)）—— 见下 |
| 字级 | span 时间合法；`span ⊆ p`；同层字时间不重叠；**包装层必须包住子 span** |
| 跨行 | 同一演唱者相邻行不重叠（和声层豁免） |
| 语义 | **整行只有 `x-bg`** → 警告"AMLL 解析后主歌词为空、播放器看不见"（[:372-378](../ttml_check.py)） |
| 合理性 | 字时长过短（<0.08 s）/过长（>2.5 s）；行内长停顿（>1.5 s）；空行 |
| 风格 | 行尾标点、英文大小写、屏蔽词（调 `lyric_style.lint_text`） |
| 全局 | `itunes:key` 连续性；`body@dur` ≥ 最后一字结束时间 |

**两种模式**：`strict=True` 把 AMLL 宽松时间写法判为**错误**；
`strict=False` 降级为**警告**（用于校验外部文件）。CLI 对应
`--check-only`（宽松）/ `--check-only --strict-time`（严格）。

### 10.4 真 AMLL 解析器验证（`tools/verify_amll_parse.py`）

**为什么需要**：自己的校验器只查"规范"，查不出**语义**问题。
最典型的是铁律 #15：用**未知 role 的 span 包住主唱 span** 时，
AMLL 解析器走 `processWordElement`，它**不递归子节点**、只在包装层自己带 begin/end 时才产出一个词
→ **整行被当成一个词**，逐字时间轴全丢、播放器一片空白。
实测：32 行 266 字 → 解析出"32 个字"。

所以 `pipeline` 第 6.5 步（[pipeline.py:324-353](../pipeline.py)）会：
**用真正的 AMLL 解析器再解析一遍**，逐行比较"字数 vs 文本长度"，
任何一行塌成一个词就报警告。解析器不可用时静默跳过（绝不因附加检查把主流程搞挂）。

该工具首次会自动抓 npm 包到 `.tmp/amll-parser/`，**不需要 npm**。

## 11. 编辑台（P1）

### 11.1 为什么需要它

自动生成已经能到 90% 以上，但总有个别字不准、个别行"谁唱的"判错。
与其让用户去外部编辑器，不如把微调收进自己的闭环（竞品对照见 `竞品调研与优化方案.md`）。

**核心设计约束**（[edit_api.py:1-12](../edit_api.py)）：
**微调阶段绝不重跑 ASR** —— 全部是毫秒级操作。

### 11.2 编辑态模型（`ttml_model.py`）

```python
EditDoc                                  # ttml_model.py:133
  lines: List[EditLine]
  meta / agents / timing / lang
  version: int          # 乐观锁版本号
  duration: Optional[float]
  write_options: dict   # ⭐ 源文件当初怎么写的（见 §11.4）

EditLine                                 # :60
  key / xml_id / text / agent / role / translation / paragraph
  begin / end
  words: List[EditWord]
  locked: bool          # 用户锁定：规范化不主动改这一行

EditWord                                 # :32
  text / begin / end
  is_bg / layer         # main / bg / translation
  prob / matched / muted
  index                 # 层内文本顺序（规范化算法依赖，勿按时间排）
```

**为什么不直接用 `matcher.Unit` / `AlignedLine`**：
它们是**对齐过程的中间产物**，字段围着算法转（`leading`/`trailing`/`core`/`anchored`…），
没有版本号、不适合序列化给前端（[ttml_model.py:4-9](../ttml_model.py)）。
`EditDoc` 是**给人改的**模型：可 JSON 序列化、可往返、字段名与 `matcher` 对齐。

`EditWord.start` 是 `begin` 的**属性别名**（[:47-53](../ttml_model.py)），
这样同一套规范化纯函数既能吃 `Unit` 也能吃 `EditWord`。

> ⚠️ 前端注意：JSON 字段是 **`begin`/`end`**，`start` 只是 Python 侧别名。

### 11.3 反向解析与往返（`ttml_reader.py`）

`parse_ttml(text) -> EditDoc` 把一份 TTML 读回编辑态模型。
**往返不变量**（selftest 第 13 组锁死）：

```
parse_ttml(write(doc)) == doc        # 时间与文本等价
write(parse_ttml(text)) == text      # 对三份真实产物**逐字节一致**
```

### 11.4 保存保真：只改用户改的（真实踩过的 bug）

**症状**：保存一个 Apple 模式的文件时，`<p ttm:role="x-duet-a">` **整个被删掉** ——
而那正是 Apple Music 左右分栏依赖的东西；还会凭空加 `itunes:songPart`、
把 `v2` 的 `type="other"` 改成 `person`。

**根因**：回写时 `make_writer` 把 `mode="amll"` / `markers="agent"` 写死了。

**修法**：`parse_ttml` 把"源文件当初怎么写的"记进 `EditDoc.write_options`
（mode / markers / line_id / time_format / translation_style / song_part / label_sections），
回写照原样；`agent_types` 也一起带回去。
另外 `parse_ttml` 以前**没读行级 `ttm:role`**，这也是角色丢失的原因之一，已修。

**验收**：三份真实产物现在**逐字节往返一致**（`selftest.py` 第 20 组守着）。

**已知残留**：源文件 `<span ttm:role="x-bg">` 若没写 `begin`/`end`，回写会补上
（属规范化；我们自己的写器一直写时间，规范说这段可选）。

### 11.5 时间轴自动修复（`ttml_normalize.py`）—— 差异化重点

**设计要点：一份算法两处用**（[ttml_normalize.py:10-16](../ttml_normalize.py)）。
"检测"在 `ttml_check.py`，"修复"原本只存在于 `matcher` 的生成阶段。
这里把**那三个函数原样抽成纯函数**：

- 生成链路：`matcher` 调用 → 行为与抽取前完全一致（selftest 锁死）；
- 编辑链路：`normalize_timeline(doc)` 调用**同一份**
  → 保证"AI 生成的允许的重叠"和"人工改后的修复"遵循**完全相同**的时间规则。

**否则就会出现"自动生成允许的重叠，手动改一下就被判非法"的自相矛盾体验。**

规则表（[ttml_normalize.py:18-30](../ttml_normalize.py)）：

| 规则 | 含义 | 修复策略 |
|---|---|---|
| R1 | 字倒序 / `begin >= end` | 按文本顺序前向游标推开 |
| R2 | 行内字重叠 | 同上（main / bg / translation 三层各自处理） |
| R3 | 字越出行区间 | 夹紧到行区间，必要时回推 start |
| R4 | 同 agent 相邻行重叠 | 把上一行末尾收到 `下一行 begin - 0.01` |
| R5 | 字时长过短（<0.08 s） | 拉长到最小字长 |
| R6 | 字时长过长（>2.5 s） | 截到最大字长 |
| R7 | 行内长停顿（>1.5 s） | **不自动修**，只进 `unresolved` |

**必须保留的例外**（[ttml_normalize.py:32-36](../ttml_normalize.py)）：

- **和声层允许与主唱重叠**（AMLL 规范："因混音而使时间重叠的情况除外"）——
  规范化只按层内处理，**绝不把和声层和主唱层压成互不重叠**；
- **行锁**：`EditLine.locked` 为真时跳过 R1–R6，只在报告里提示。

阈值与 `matcher` / `ttml_check` 严格对齐（[ttml_normalize.py:46-53](../ttml_normalize.py)），
避免两套逻辑漂移。

### 11.6 后端逻辑（`edit_api.py`）

**纯函数，不碰 HTTP**（[edit_api.py:1-12](../edit_api.py)），方便离线自测；
`web_server.py` 只做"取参 → 调这里 → 返回 JSON"。

| 函数 | 职责 |
|---|---|
| `load_doc()`（[:87](../edit_api.py)） | 读取编辑态：内存 → `.edit.json`（`source=disk`）→ 由 TTML 重建（`source=draft`） |
| `validate()`（[:148](../edit_api.py)） | **只算不写**；**深拷贝**后规范化，绝不动调用方的 doc；返回修复后的 doc |
| `apply_doc()`（[:162](../edit_api.py)） | 就地规范化 + 校验 + 原子落盘 + 版本 +1 |
| `check_version()`（[:180](../edit_api.py)） | 乐观锁 |
| `atomic_write_text()`（[:48](../edit_api.py)） | 先写同目录临时文件 → `fsync` → `os.replace` |

**为什么 `validate()` 要返回修复后的 doc**（[:151-153](../edit_api.py)）：
前端拖完一个字要立刻显示"已自动修复"后的时间，否则界面还停在坏时间上。

**乐观锁的关键细节**（[:180-197](../edit_api.py)）：
必须拿**存储里的 version** 和前端带来的比。
**不能拿提交体里的 `doc.version` 自比**（那样永远相等，锁形同虚设）。
不一致 → `EditError(code=409)`。

**结构化错误契约**（[:30-44](../edit_api.py)）：

```json
{ "error": "人类可读的中文原因", "where": "定位", "detail": "技术细节",
  "hint": "下一步建议做什么", "code": 400 }
```

`do_GET` / `do_POST` 都兜底捕获 `EditError` → 返回结构化 JSON 而不是断连接
（[web_server.py:138-145](../web_server.py)、[:185-201](../web_server.py)）。

### 11.7 HTTP 端点（[web_server.py](../web_server.py)）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` `/index.html` | Web UI |
| GET | `/api/task?id=` | 任务状态 + 日志 + 进度 |
| GET | `/api/ttml?id=` | 最新 TTML 文本 + summary |
| GET | `/api/download?id=` | 下载 TTML |
| GET | `/api/edit?id=` | **载入编辑态**（doc + version + source + stats） |
| POST | `/api/upload` | 上传（base64，上限 `MAX_UPLOAD_MB`，文件名清洗） |
| POST | `/api/convert` | 启动转换（异步线程） |
| POST | `/api/edit` | **保存**：乐观锁 → 规范化 → 校验 → 落盘 |
| POST | `/api/validate` | **只校验**（供前端节流调用） |

**任务模型**：内存 `TASKS: dict`，`Task` 持有 params/status/progress/stage/logs/error/
`ttml`/`summary`/`edit_path`/`doc`（[web_server.py:47-100](../web_server.py)）。
转换在**独立线程**里跑（`threading.Thread`），
进度由日志前缀映射（`STAGE_PROGRESS`）+ 正则抽取"乐句 x/y"（[:71-82](../web_server.py)）。

**生成完立即建立编辑态**（[web_server.py:362-368](../web_server.py)）：
`edit_api.doc_from_ttml()` + `save_doc()` 写出 `outputs/<id>.edit.json` 初始快照
（失败只记日志，仍可下载 TTML）。

**失败不崩**：`_run_task` 的 `except Exception` 把错误写进 `task.error` +
日志末尾 8 行 traceback（[:389-396](../web_server.py)）。

### A.4 值得注意的实现细节（附带事实）

- `speaker_campplus.fbank` 的 docstring 声称"与 Kaldi `snip_edges=True` 一致"，但代码先 pad 了一帧长度再计帧，等价帧数为 `1 + L//160`（Kaldi 是 `1 + (L-400)//160`）—— 1 秒音频多约 3 帧。因为网络用 `output_level="segment"` 做整段池化，影响有限（**静态推断，未实测**）。
- `speaker_campplus.embed` 每次调用都会 `_pick_device()`，且 `net.to(dev)` 是对**全局共享模型**的原地搬迁，没有锁保护（[speaker_campplus.py:160-167](../speaker_campplus.py)）。
- `textread.read_text_with_encoding` 用裸 `open(path,"rb").read()`（没有 `with`），文件句柄依赖 GC 关闭（[textread.py:83](../textread.py)）。
- `write()` 会**就地修改**传入的行对象补 `agent="v1"`（[ttml_writer.py:289-292](../ttml_writer.py)）；调用方若复用同一批 `AlignedLine` 需注意这个副作用。
- `read_text_best_effort` 的 `dirty` 只做到"提示"，不阻断：Big5 繁体目前**不会被正确解码**，只会被标成可疑。

### A.5 已修复：无小数秒的 LRC 曾被判成纯文本（精度坑，2026-10-09 修）

**现象**：`[00:04]`（无小数秒）形式的 LRC 在实际歌词里很常见，
但整份文件会被判成**纯文本**，带来两个后果：

1. **丢掉全部行级锚点** → `matcher` 走"全曲全局对齐"路径（§7.4(b)），精度明显下降；
   用户明明给了带时间戳的 LRC，却得到"纯文本级"的待遇。
2. **时间戳文本进了歌词** → `[00:04]` 被当成正文留在 `line.text` 里，一路写进 TTML 的 `<span>`。

**根因**：两条正则严格度不一致 ——
判定用 `^\[\d+:\d+\.\d+\]`（**要求**小数秒），提取用 `\[(\d+:\d+\.?\d*)\]`（**可选**）。

**修复**（[preprocess.py:221](../preprocess.py)）：判定正则的小数秒改为可选
`r'^\[\d+:\d+(?:\.\d+)?\]'`，与提取正则对齐；`parse_time_lrc` 同步放宽为
`(\d+:(?:\.\d+)?)` 保持一致。**只改判定一处，解析能力本就不缺**。

**验证**（`selftest.py` 第 21 组，9 条断言）：

| 输入 | 修复前 | 修复后 |
|---|---|---|
| `[00:04]甲 / [00:08]乙` | 无锚点、`[00:04]` 泄漏进歌词 | **有锚点**、时间正确、无泄漏 |
| `[00:04.37]…`（原有路径） | 正常 | 正常（毫秒保留） |
| 混用 `[00:04]` + `[00:08.19]` | 整份判定失败 | 两行都有锚点 |
| 一行多戳 `[00:04][00:08.19]甲` | — | 展开成 2 行、都不带戳 |
| `[ti:]/[ar:]` 元信息行 | 跳过（正常） | 跳过（未回归） |
| 空行分段 | paragraph 递增（正常） | 未回归 |
| 纯文本 | 无锚点（正常） | 未回归 |
